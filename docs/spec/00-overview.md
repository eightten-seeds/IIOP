## 1. 文档目的

本文档用于固定 IIOP 的项目边界、业务主线、系统架构、微服务职责、数据归属、技术基线、客户端范围、AI 能力边界、非功能目标和最终验收口径。

本文档承担“项目总纲”角色。后续数据库、后端、PC、HarmonyOS、AI 和开发路线等专项规范必须与本文档保持一致。

当专项规范与本文档发生冲突时：

1. 已经被真实代码和测试验证的实现事实优先保留；
2. 尚未实现的设计冲突以本文档为上位约束；
3. 任何需要改变微服务边界、核心业务闭环或技术基线的修改，必须先修改本文档，再修改代码；
4. Codex 不得自行改变项目边界。

## 2. 项目问题定义

### 2.1 业务背景

工业设备巡检与运维通常涉及设备台账、周期巡检、实时监测、异常上报、设备告警、维修工单、维修验收和历史追溯等多个环节。

本项目要解决的核心问题，是把这些原本分散的环节组织成一个可追踪的业务闭环，并在其中加入大语言模型辅助诊断能力，使设备异常能够结合设备资料、监测指标、巡检历史、维修历史和 SOP 得到结构化分析结果。

### 2.2 项目目标

IIOP 最终必须形成以下完整链路：

设备建档  
→ 配置巡检模板  
→ 制定巡检计划  
→ 生成巡检任务  
→ PC 或 HarmonyOS 执行巡检  
→ 记录正常项或发现异常  
→ 形成异常、缺陷或设备告警  
→ DeepSeek 辅助诊断  
→ 人工确认诊断结果  
→ 创建或完善维修工单  
→ 维修处理  
→ 维修验收  
→ 关闭工单  
→ 沉淀为设备生命周期数据

系统价值主要体现在四个方面：

1. 将设备、巡检、异常、维修和 AI 诊断串成一条可追溯链路；
2. 通过微服务体现清晰的业务领域边界；
3. 通过 PC 与 HarmonyOS 实现管理端和现场端协同；
4. 通过 DeepSeek、LangChain4j 和 LangGraph4j 实现可解释、可追踪、需要人工确认的智能诊断流程。

## 3. 已确定要求、工程决策与待验证事项

为了避免 Codex 把“项目要求”“当前设计”和“尚未验证的假设”混在一起，后续开发必须区分三类内容。

### 3.1 已确定要求

以下内容已经确定，后续实现不得自行删除：

- 项目必须采用微服务架构；
- 后端使用 JDK 17；
- 使用 Spring Boot 3.5.0；
- 使用 Spring Cloud 2025.0.0；
- 使用 Spring Cloud Alibaba 2025.0.0.0；
- 使用 MySQL、MyBatis-Plus、Redis；
- 使用 Sa-Token；
- 使用 Nacos、Sentinel、RocketMQ；
- AI 侧必须包含 DeepSeek、LangChain4j、LangGraph4j；
- PC 端采用 Vue 3、Axios、Pinia、Element Plus；
- PC 端必须体现 ECharts、Three.js、Vue Flow；
- 必须提供 HarmonyOS 移动端；
- 系统包含 WebSocket 实时通信能力；
- 最终需要完整项目源代码；
- 最终正式答辩材料只计划生成：
  1. 团队项目实训报告；
  2. 个人实训报告；
  3. 答辩 PPT；
  4. 答辩讲稿。

### 3.2 当前工程决策

以下属于当前设计方案。它们具有明确工程理由，但在真实实现出现充分证据时允许受控调整：

- 后端划分为 6 个可启动服务和 1 个公共 Jar 模块；
- 一个 MySQL Server 中划分 5 个逻辑数据库；
- 每个业务微服务只直接访问自己的数据域；
- 跨服务关联保存业务 ID，不建立跨库物理外键；
- 服务同步查询优先使用 REST/OpenFeign；
- 跨领域状态变化和异步业务优先使用 RocketMQ；
- WebSocket 用于实时通知，不作为业务事实的唯一存储；
- Redis 用于会话、缓存、幂等和实时状态快照，不作为主业务数据库；
- AI 诊断结果必须持久化并保存人工确认状态；
- HarmonyOS 聚焦现场巡检与维修场景，不复制 PC 全量后台能力。

### 3.3 暂不固定的事项

以下内容必须在真正引入依赖或实现功能时再确定：

- MyBatis-Plus 具体版本；
- Sa-Token 具体版本；
- LangChain4j 具体版本；
- LangGraph4j 具体版本；
- Vue、Vite、Element Plus 等前端依赖的具体小版本；
- HarmonyOS API Level 和 DevEco Studio 具体版本；
- DeepSeek 最终使用的模型名称；
- 本地基础设施采用原生安装还是 Docker；
- 是否增加对象存储、向量数据库或其他中间件。

Codex 不得为了“完整”而提前猜这些版本或额外引入组件。

## 4. 用户角色与权限边界

第一版系统固定四类业务角色。

### 4.1 SUPER_ADMIN

超级管理员拥有系统级管理权限，主要负责：

- 用户管理；
- 角色管理；
- 权限管理；
- 系统级数据查看；
- 设备基础数据管理；
- 系统配置维护；
- AI 配置项的可见性控制；
- 平台整体运行检查。

### 4.2 ADMIN

业务管理员负责日常业务维护，主要包括：

- 设备分类和设备台账维护；
- 巡检模板和巡检计划维护；
- 告警和缺陷查看；
- 工单分派；
- 统计分析；
- 业务数据维护。

ADMIN 不默认拥有修改系统安全配置和超级管理员权限的能力。

### 4.3 INSPECTOR

巡检人员面向现场巡检业务，主要包括：

- 查看分配给自己的巡检任务；
- 开始巡检；
- 填写巡检项；
- 上传巡检证据；
- 上报异常；
- 查看与自己任务相关的设备信息；
- 查看任务处理结果。

### 4.4 MAINTAINER

维修人员面向维修工单，主要包括：

- 查看分配工单；
- 接单或开始处理；
- 查看设备信息、异常信息和 AI 辅助诊断；
- 填写故障原因；
- 填写维修方案；
- 记录配件、费用和停机时间；
- 提交维修结果；
- 等待验收。

权限必须通过 Sa-Token 和系统 RBAC 数据共同控制。

## 5. 核心业务对象

系统围绕以下业务对象构建。

### 5.1 设备

设备是整个平台的核心实体。

设备至少需要包含：

- 唯一设备编码；
- 名称；
- 分类；
- 型号；
- 制造商；
- 序列号；
- 安装位置；
- 车间；
- 产线；
- 责任人；
- 当前状态；
- 风险等级；
- 安装时间；
- 质保信息；
- 三维模型地址；
- 三维场景位置。

设备是巡检任务、异常、告警、缺陷、工单和 AI 诊断的共同关联对象。

### 5.2 巡检模板

巡检模板描述“检查什么”。

模板由多个检查项组成，每个检查项可以包含：

- 项目名称；
- 类型；
- 单位；
- 标准值；
- 上下限；
- 检查方法；
- 是否必填；
- 异常提示。

### 5.3 巡检计划

巡检计划描述“什么时候、由谁、对哪台设备执行哪套模板”。

计划负责周期性产生巡检任务。

### 5.4 巡检任务

巡检任务是实际执行单元。

任务创建时必须形成模板快照，后续模板发生修改时，历史任务内容不得随之变化。

### 5.5 巡检异常

巡检过程中某个检查项出现超限、故障迹象或人工判断异常时产生巡检异常。

异常必须记录：

- 来源任务；
- 来源检查项；
- 设备；
- 严重程度；
- 描述；
- 图片或其他证据；
- 上报人；
- 上报时间；
- 当前状态。

### 5.6 告警

告警可以来自：

- 设备监测指标；
- 巡检异常；
- 人工创建。

告警强调“系统发现需要关注的异常状态”。

### 5.7 缺陷

缺陷是维护域中统一承接后续处理的业务对象。

巡检异常、设备告警或人工发现的问题，都可以归一化为缺陷。

### 5.8 维修工单

维修工单承担异常处理闭环。

典型状态：

DRAFT  
→ PENDING  
→ ASSIGNED  
→ PROCESSING  
→ WAITING_ACCEPTANCE  
→ COMPLETED

同时允许 CANCELLED。

### 5.9 AI 诊断

AI 诊断是对异常或告警的辅助分析记录。

它必须关联：

- 触发来源；
- 设备；
- 使用的模型；
- Prompt 版本；
- 风险等级；
- 可能原因；
- 排查步骤；
- 维修建议；
- 安全提示；
- 工作流轨迹；
- 人工确认状态。

## 7. 总体架构

系统按“客户端层 → 网关层 → 业务服务层 → 基础设施层 → 数据层”组织。

### 7.1 客户端层

包含：

- Vue 3 PC 管理端；
- HarmonyOS ArkUI 移动端。

两个客户端统一通过网关访问后端。

客户端禁止直接访问数据库或 Nacos。

### 7.2 网关层

iiop-gateway 是所有业务 HTTP 请求的统一入口。

主要职责：

- 路由；
- 登录态协同；
- 基础权限前置判断；
- Sentinel 网关限流；
- 跨域；
- 统一请求头处理；
- 请求追踪信息透传。

网关不承担具体业务逻辑，不拥有业务数据库。

### 7.3 业务服务层

可启动服务固定为：

- iiop-gateway；
- iiop-auth；
- iiop-device；
- iiop-inspection；
- iiop-maintenance；
- iiop-ai。

iiop-common 为普通 Jar，不启动。

### 7.4 基础设施层

包括：

- Nacos：服务发现和配置管理；
- Redis：会话、缓存、状态快照、幂等；
- RocketMQ：业务事件；
- Sentinel：限流和保护；
- WebSocket：实时通知；
- DeepSeek：大模型推理能力。

### 7.5 数据层

使用一个 MySQL 8.x 实例，规划五个逻辑数据库：

- iiop_auth；
- iiop_device；
- iiop_inspection；
- iiop_maintenance；
- iiop_ai。

## 9. 服务间依赖关系

允许的同步依赖：

| 调用方 | 被调用方 | 用途 |
|---|---|---|
| inspection | device | 查询设备、设备分类、设备上下文 |
| inspection | auth | 获取必要用户摘要 |
| maintenance | device | 查询设备信息 |
| maintenance | auth | 查询人员信息 |
| ai | device | 获取设备、监测指标、SOP |
| ai | inspection | 获取近期巡检和异常历史 |
| ai | maintenance | 获取维修历史 |
| maintenance | ai | 查询已生成的 AI 诊断结果 |

调用规则：

1. 服务不得查询其他服务数据库；
2. 同步调用只获取当前业务操作真正需要的数据；
3. Feign DTO 与数据库 Entity 分离；
4. 调用失败需要明确超时和降级行为；
5. 禁止形成同步循环调用。

## 10. 核心业务流程

### 10.1 设备建档

管理员创建设备分类  
→ 创建设备  
→ 配置状态和风险等级  
→ 可配置监测指标  
→ 可关联 SOP  
→ 可配置三维模型和场景坐标  
→ 设备进入可巡检状态

### 10.2 巡检任务生成

管理员创建巡检模板  
→ 配置模板项  
→ 创建巡检计划  
→ 计划关联设备、模板、执行人和周期  
→ 系统按计划生成任务  
→ 生成任务项快照  
→ 巡检人员收到任务

### 10.3 现场巡检

巡检人员打开任务  
→ 开始任务  
→ 查看设备和检查项  
→ 逐项填写结果  
→ 必要时上传证据  
→ 正常项保存为 NORMAL  
→ 异常项保存为 ABNORMAL  
→ 产生巡检异常  
→ 完成任务

### 10.4 异常处理

巡检异常产生  
→ inspection 持久化异常  
→ 发布 RocketMQ 异常事件  
→ maintenance 消费事件并形成缺陷或告警  
→ ai 消费事件并创建诊断任务  
→ auth/通知逻辑向相关人员发送通知

### 10.5 AI 诊断

AI 收到诊断触发  
→ 加载设备基础信息  
→ 加载设备近期监测信息  
→ 加载近期巡检历史  
→ 加载维修历史  
→ 加载 SOP  
→ DeepSeek 结构化分析  
→ 风险检查  
→ 生成维修建议  
→ 保存诊断结果  
→ 保存每个 LangGraph4j 节点轨迹  
→ 等待人工确认

### 10.6 维修闭环

缺陷存在  
→ 创建工单  
→ 分派维修人员  
→ 开始处理  
→ 查看 AI 诊断和历史资料  
→ 填写实际故障原因和维修措施  
→ 提交维修结果  
→ 进入 WAITING_ACCEPTANCE  
→ 验收  
→ 通过则 COMPLETED  
→ 驳回则重新进入处理流程  
→ 维修历史沉淀到设备生命周期

## 12. Redis 使用边界

Redis 只用于可重新构建的数据或短期状态。

允许场景：

- Sa-Token 登录会话；
- 权限缓存；
- 设备实时状态快照；
- 首页统计短缓存；
- RocketMQ 消费幂等键；
- WebSocket 在线用户辅助信息。

建议命名：

- iiop:auth:permission:{userId}
- iiop:device:status:{deviceId}
- iiop:dashboard:overview
- iiop:event:consumed:{eventId}

Redis 中的数据丢失不得导致核心业务历史不可恢复。

## 14. WebSocket

WebSocket 用于实时通知。

通知类型：

- ALARM；
- INSPECTION；
- WORK_ORDER；
- AI；
- SYSTEM。

基本原则：

1. 通知事实先持久化；
2. WebSocket 只负责实时送达；
3. 客户端断线后可通过 REST 查询历史通知；
4. 客户端需要断线重连；
5. WebSocket 不承担工单状态等核心业务状态存储。

模型无法获得充分上下文时，必须允许输出“信息不足”，不得强制生成确定结论。

## 19. 非功能目标

以下属于项目验收目标，不代表当前已经实现。

### 19.1 可维护性

- 每个微服务职责清晰；
- Controller、Service、Mapper 分层明确；
- DTO、VO、Entity 职责区分；
- 状态枚举集中管理；
- 禁止跨服务直接访问数据库；
- 核心配置集中管理；
- 错误返回统一。

### 19.2 安全性

- 密码只保存哈希；
- 密钥不得进入 Git；
- 重要接口必须鉴权；
- 权限必须由后端执行；
- 参数必须校验；
- 对敏感操作保留日志；
- AI 高风险结论必须人工确认。

### 19.3 性能目标

第一版目标值：

- 普通 CRUD API 在本地开发环境下应保持可交互响应；
- 驾驶舱常规查询通过缓存和聚合避免大量重复 SQL；
- 设备监测历史按设备和时间建立索引；
- DeepSeek 请求采用独立超时配置；
- AI 请求不得阻塞整个业务服务；
- WebSocket 消息以实时交互体验为目标。

具体毫秒级指标只有在形成真实测试环境后再写入最终测试报告。

### 19.4 可用性

- 单个外部 AI 请求失败不能导致设备、巡检、工单基础业务不可使用；
- DeepSeek 不可用时，诊断记录应明确失败或降级；
- WebSocket 断开后，通知历史仍可查询；
- Redis 缓存丢失后，核心业务数据仍可从数据库恢复。

## 21. API 总体规则

- /api/auth
- /api/device
- /api/inspection
- /api/maintenance
- /api/ai

统一响应结构：


分页参数：

分页返回至少包含：

- total；

约束：

- 接口参数必须校验；
- Entity 不直接作为跨服务 API 契约；

- 时间输出统一；
- 业务状态使用英文枚举编码；
- HTTP 状态与业务错误码保持逻辑一致。

## 22. 数据一致性原则

本项目第一版不追求复杂分布式事务框架。

采用：

本地事务  
+ 业务事件  
+ 幂等消费  
+ 最终一致性

原则：

1. 服务内关键写操作使用本地事务；
2. 跨服务状态传播使用 RocketMQ；
3. 消费端必须防止同一 eventId 重复处理；
4. 业务历史不得依赖实时跨服务查询才能解释；
5. 任务、工单等关键对象保存必要快照；
6. 不为了“强一致”制造复杂的跨服务数据库事务。
